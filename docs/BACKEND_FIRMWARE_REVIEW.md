# Backend and STM32 communication review — November 16, 2026

## Scope and outcome

Reviewed the checked-out FastAPI backend, Python serial adapter, motor runner,
sensor ownership, firmware protocol, and motor state machine. The current ADS
firmware and backend agree on the wire contract. This is source/host validation,
not evidence of the installed Pi software, flashed STM32 image, USB reliability,
physical relay behavior, sensor accuracy, or a real motor run.

## Contract checked

| Item | Backend and firmware |
|---|---|
| Link | ST-LINK USART2, 115200 baud, 8 data bits, no parity, 1 stop bit, no flow control |
| Protocol | ADS version 1, one ASCII JSON message per newline |
| Integrity | CRC32 of the JSON body, appended as `*` plus eight hexadecimal digits |
| Device identity | Requests use raspberry-pi; replies use STM32-ADS |
| Correlation | Each response payload's reply_to matches the request sequence |
| Motor setup | Capabilities/status, sequence synchronization, fresh heartbeat, ARM_TEST |
| Supply preparation | PREPARE_TEST_POWER with zero PWM; wait for POWER_READY |
| Start | SET_PWM followed by START_TEST with pwm_percent, duration_ms, FORWARD |
| Completion | Matching MOTOR_START/MOTOR_STOP events, zero-output STOP_TEST acknowledgment |
| Firmware settings | 0.7.0-downstream-protected; 50% PWM; maximum 30000 ms |
| Electrical contract | 10–14 V, absolute current below 1.5 A; downstream power check |
| Communication protection | STM32 heartbeat-loss shutdown at 2000 ms |
| Recorded results | Raw measurements, acknowledgments/events, durable run record and CSV export |

The firmware accepts at most 512 JSON request bytes while Python can decode
replies up to 4096 bytes. These are directional limits: current backend motor
requests fit the firmware limit, and the larger firmware replies fit Python's.
Future command payloads must respect the smaller request limit.

The serial transport takes an exclusive port lock. Sensor polling and motor
operations share the engine mutex. A separately launched verifier or terminal
must not compete with the dashboard backend for that USB connection.

## Corrections

1. The JSON connection verifier formerly required hardware_control=false. It now
   accepts enabled firmware only when zero PWM and relay-command-off are reported.
   It rejects active/unknown output before sending a heartbeat. The probe never
   sends ARM, power preparation, PWM, Start or Stop commands.
2. The motor snapshot's ready field formerly depended on the Pi's separate
   circuit-enable flag. It now reflects the fresh firmware snapshot; the circuit
   flag is still reported and still controls circuit authorization. This cached
   snapshot does not authorize a motor start or prove physical readiness.
3. A normal stop can remove downstream sensor voltage while the backend is
   receiving its last sample. The backend no longer turns that expected zero
   into a running undervoltage failure when STM32 status explicitly reports
   STOPPED, COMPLETED, zero applied PWM and relay-command-off. The correlated
   completion event and final stopped acknowledgment remain required. Startup,
   running undervoltage, overvoltage and overcurrent checks remain enforced.

No production STM32 code or physical-output limits were changed in this review.
Existing unrelated working-tree edits were preserved.

## Cross-language verification

tests/backend_firmware_harness.c compiles the production ads_protocol.c,
ads_test.c and ads_acquisition.c with the canonical downstream operator profile.
Only hardware callbacks and time are fixture implementations; no GPIO or USB
port is accessed. Requests are generated by STM32SerialConnection, parsed by
the actual C implementation, and C replies are decoded by the production Python
adapter. Fixture sessions are replayed with recorded request ticks to avoid OS
process scheduling changing their acquisition timestamps.

tests/test_backend_firmware_contract.py covers:

- A read-only capabilities/status/measurement handshake with no actuation writes.
- The JSON verifier against enabled but stopped C firmware.
- Backend motor preparation, 50% Start, acquisition, completion and CSV export.
- The FastAPI preflight, hardware-run and CSV endpoints against that C exchange.
- Wrong-duty rejection with the actual PWM_OUT_OF_RANGE reason and cleanup Stop.
- Missing motor supply preventing SET_PWM and START_TEST.
- Zero downstream voltage after confirmed normal completion.

Fixtures save to temporary databases. Their values are synthetic hardware inputs
and must not be presented as measured Trace-X experimental results.

Validation: all 236 tests passed with
`.venv/bin/python -m unittest discover -s tests` (34.435 seconds).

## Remaining Pi bring-up

1. Flash the consolidated ADS project with the 12 V motor supply disconnected.
2. Deploy the matching current backend and built frontend to the Pi. This review
   did not copy files to the Pi or restart its service.
3. In the Pi's Python environment run `python3 -m serial.tools.list_ports -v`.
   Put the actual ST-LINK USB serial number in a private hardware profile's
   serial_identity. The supplied supervised-operator-profile.json leaves it blank.
4. Set ADS_AUTOMATION_HARDWARE_PROFILE to that profile's absolute path in the
   backend's environment. A path/baud setting alone does not replace USB identity.
   ADS_HARDWARE_CONTROL_ENABLED is a circuit permission, not a direct motor gate.
5. With other serial readers/backend stopped, verify the new request/response
   firmware using the actual port:

   `python3 -m diagnostic_platform.verify_stm32 --protocol json --crc32 --port /dev/ttyACM0`

   Replace the example port if device discovery reports a different one. Passive
   auto detection can time out on this firmware because it waits for requests.
6. Restart the backend and use the STM32 motor test panel's Check hardware.
   Confirm the returned firmware, enabled output capability, stopped state and
   fresh sensor records. A software snapshot does not verify relay contacts.
7. After physical checks, request 50% forward PWM for a short bounded test.
   Verify real Start, Stop, readings and saved CSV before assessing motor health.

Uncalibrated encoder scaling and absent approved baselines can leave health
analysis insufficient while motor capture still succeeds. Temperature is disabled.
